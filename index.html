Sortable audit table: keep the announced order true

Change the sort and inspect the row order, active header state, and keyboard focus together.

An audit dashboard can look sorted while its accessibility state still names the previous column. It can also update a sort icon without moving the rows. This lab makes each part observable. The rows are illustrative tasks, not actual ADAFix findings or a claim about any website.

Keyboard and DOM test

  1. Tab to Priority and press Enter or Space. Focus should stay on that button.
  2. Read the first-column task order. Priority 1, 2, 3 should now follow each other in the DOM; the order is not a CSS-only illusion.
  3. Inspect the column headers. Only Priority should have aria-sort="ascending". The Issue header should have no aria-sort attribute.
  4. Activate Priority again. Rows should reverse, its header should say descending, and the status text should match.
  5. Try the same path at high zoom and with the browser/assistive technology combinations that matter to your users.

This example uses native table, th and button elements. It does not give the whole table an interactive grid role. Review-step cells are read-only and are not extra tab stops.

Why the state belongs on the header

The W3C ARIA Authoring Practices sortable-table example places aria-sort on the currently sorted column header, with a button inside each sortable header. When another column becomes active, the attribute moves with it. The APG example also warns that illustrative code needs testing with real browsers and assistive technologies before production use.

To review a real source change, keep the observed behavior, affected component, proposed repair and post-deployment retest together. ADAFix’s accessibility remediation workflow describes this source-review and verification process. A sorted-looking screenshot or scanner result alone cannot establish the order a keyboard and screen reader user encounters.
